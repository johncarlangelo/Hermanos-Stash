## Feature 1: Batch Queue Runner

**Goal:** Chain tools into a single runnable queue (drag N files → one drop → `tool A → tool B → tool C` in sequence).

### Architecture

- New tool: `batch-queue` (category: `developer` or `files`)
- Uses existing per-tool `supportsBatch` / `acceptsMultipleFiles` capabilities
- IPC: `queue:run` (array of `{ toolId, options }` + `inputFiles[]`)
- Progress: reuse existing `progress:start/update/end/cancel` channels (they're already tool-agnostic)
- History: one parent "Queue run" entry + child per-step entries

### Data model

```ts
interface QueueStep {
  toolId: string
  options: Record<string, unknown>  // per-tool options snapshot
}

interface QueueSpec {
  name: string
  steps: QueueStep[]
}

interface QueueRunInput {
  spec: QueueSpec
  inputFiles: string[]  // absolute paths
}
```

### UI

- **Builder panel** (left): draggable step list (reorder, add, remove)
  - Add step → tool picker (filters to tools with `supportsBatch` or `acceptsMultipleFiles`)
  - Per-step options editor (reuse the tool's own option UI components via dynamic import)
- **Runner panel** (right): drop zone + progress + results
  - Drop files → shows count + validates against step 1's `accept` extensions
  - Run button → kicks off IPC `queue:run`
  - Live progress per step (overall + current-step)
  - Results table per step (expandable)

### Persistence

- `queues` table (SQLite): `id, name, spec_json, created_ms, updated_ms`
- Prefs: last-used queue name, recent queues (for palette quick-pick)

### IPC (main)

```ts
// src/main/ipc/register.ts
handle(IPC.queueRun, async (_e, input: QueueRunInput) => {
  // 1. Validate all steps exist + have batch capability
  // 2. For each step:
  //    - Invoke the tool's main-side handler with its options + files
  //    - Collect output files → feed as input to next step
  //    - Emit progress events for the whole pipeline
  // 3. Return final outputs
})
```

## Feature 2: Usage Dashboard

**Goal:** "What have I done?" view — top tools, space saved, file types, recency.

### Data source

- Existing `activity` table has: `tool_id, operation, inputs_json, outputs_json, status, duration_ms, message`
- Join with `outputs_json` (file paths) → `fs.stat` for sizes → compute savings
- No new storage needed; reads from existing DB

### Metrics

- **Top tools** (last 7/30 days): count, success rate, avg duration
- **Space saved**: sum of `(input_bytes - output_bytes)` for successful media ops
- **File types processed**: aggregate extension counts from `inputs_json`
- **Timeline**: weekly activity sparkline (bar chart, last 12 weeks)
- **Recent queue runs** (if queue runner exists)

### UI

- New view: `dashboard` (sidebar: "Usage")
- Grid of metric cards + chart + recent activity table
- Time-range picker: 7d / 30d / 90d / all
- Click a tool card → opens that tool pre-filled with last options

### Chart

- Reuse `recharts` (already in deps via brand-bible) or lightweight custom SVG bars (fewer deps)
- Dark-theme, matches token palette (`--color-accent`, `--color-ink`, `--color-faint`)
